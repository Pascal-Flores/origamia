## Reference pedagogique

Description de la competence :

> Identifier le bloc de lecture du capteur (etat/valeur), comprendre ce que signifie la lecture pour l'objet (ex. obstacle detecte / niveau lumineux) et l'exprimer clairement dans le script (etiquette/nommage utile).

Attendus :

- `109-111` : `att-lire-capteur-cm1`
  - Utiliser une donnee de capteur fournie (un seul capteur) dans le programme.
- `112-114` : `att-lire-capteur-cm2`
  - Choisir le bon capteur parmi 2 (guide) et justifier rapidement.
- `115-117` : `att-lire-capteur-6e`
  - Choisir parmi plusieurs capteurs et justifier l'adequation au besoin.

## Ce que la competence travaille

L'eleve doit comprendre qu'un capteur fournit une information au programme, dans un environnement de programmation de microcontroleur.

La tache porte sur :

- identifier quelle information est lue ;
- comprendre ce que cette information mesure ou detecte ;
- choisir dans l'interface le capteur ou le bloc de lecture adapte a une information attendue ;
- formuler pourquoi ce capteur est utile.

## Recadrage interface - 2026-07-07

Retour utilisateur : comme il s'agit de programmation de microcontroleur, les exercices doivent privilegier l'interface, sauf peut-etre en CM1.

Consequence :

- Les exercices ne doivent pas seulement parler d'un capteur dans l'abstrait.
- Les enonces doivent montrer ou decrire des elements d'interface : menu de capteurs, bloc disponible, valeur affichee, tuile de simulateur, etiquette de lecture.
- L'eleve doit faire un geste proche de l'usage reel : reconnaitre une valeur lue, choisir le bloc de capteur, associer une tuile d'interface a l'information cherchee.
- On evite de demander d'ecrire un programme complet.

## Recadrage CM1 - 2026-07-08

Retour utilisateur : il n'est pas possible de fixer une valeur precise pour le capteur dans l'interface. Pour `109-111`, il est donc plus pertinent de montrer un programme et de demander quel capteur est utilise par ce programme.

Exemple de geste attendu :

> Dans ce programme, quel capteur est utilise ?

Reponses possibles :

- thermometre ;
- microphone ;
- capteur de lumiere ;
- bouton ;
- accelerometre.

Ce cadrage est meilleur pour le CM1 parce qu'il colle a l'interface reelle : l'eleve lit un bloc de capteur present dans le programme, sans inventer de valeur de mesure.

## Ce que la competence ne travaille pas

- Pas de declenchement `si... alors`.
- Pas de pilotage d'actionneur.
- Pas de chaine complete capteur -> commande -> actionneur.
- Pas de schema de fonctionnement global.
- Pas de correction de programme.
- Pas de simulation d'etat final.

Ces objets appartiennent aux autres competences du pilier ou a l'analyse de programmes.

## Progression proposee

### 109-111 - CM1

Type propose : `qcu`.

Structure :

1. Une courte situation avec une carte programmable ou un microcontroleur.
2. Un programme est montre, idealement via une interface ou une capture de blocs.
3. Le programme contient un bloc de lecture de capteur clairement visible.
4. Question : "Quel capteur est utilise par ce programme ?"
5. Reponses : noms de capteurs, un seul correct.

But didactique :

- Lire un programme court dans l'interface.
- Reperer le bloc de lecture de capteur.
- Associer le bloc lu au nom du capteur.
- Ne pas demander de valeur precise de capteur.

Exemples de situations possibles :

- programme qui ecrit dans la console la temperature en degres Celsius : capteur thermometre ;
- programme qui ecrit le niveau sonore : microphone ;
- programme qui ecrit la luminosite : capteur de lumiere.

Support possible :

- `type: interface` avec un lien Vittascience quand l'interface est disponible ;
- sinon, image ou rendu de blocs dans l'enonce, sans valeur de capteur imposee.

Liens fournis pour les variantes CM1 :

- `109.md` : https://fr.vittascience.com/microbit/?link=6a4e0ab4cb1b1&mode=mixed&console=bottom&toolbox=vittascience&simu=1
- `110.md` : https://fr.vittascience.com/microbit/?link=6a4e0e48741b4&simu=1&toolbox=vittascience
- `111.md` : https://fr.vittascience.com/microbit/?link=6a4e0e8ebfb7f&simu=1&toolbox=vittascience

Variante pilote `109.md` :

- Programme observe : le programme ecrit dans la console la valeur `temperature en °C`.
- Capteur attendu : thermometre / capteur de temperature.
- Question : "Dans ce programme, quel capteur est utilise ?"
- Type : `qcu`.

Declinaison CM1 :

- `110.md` : capteur attendu = microphone.
- `111.md` : capteur attendu = boussole.
- Pattern valide : pas de section "Lien vers l'interface" dans le corps ; le lien reste seulement dans le frontmatter `link`.

### 112-114 - CM2

Type propose : `ddc`.

Structure :

1. Une interface propose deux blocs ou deux tuiles de capteurs.
2. Plusieurs informations a lire sont donnees.
3. L'eleve classe chaque information sous le bloc ou la tuile qui peut la fournir.

But didactique :

- Distinguer deux mesures proches mais non equivalentes.
- Justifier implicitement par le tri.
- Rester guide : seulement deux elements d'interface.

Exemples de paires :

- bloc `distance en cm` / bloc `luminosite` ;
- tuile `temperature` / tuile `humidite du sol` ;
- bloc `bouton A appuye` / bloc `inclinaison`.

Cadrage valide par l'utilisateur pour une variante pilote.

Variante pilote `112.md` :

- paire de blocs : `temperature (°C)` / `niveau sonore` ;
- geste demande : classer des informations sous le bloc de capteur qui permet de les lire ;
- pas de lien d'interface dans le corps de l'exercice ;
- pas de valeur precise imposee au capteur.

Retour utilisateur : variante pilote non valide.

Analyse du probleme :

- le tri d'informations ressemble trop a un exercice de vocabulaire ;
- le geste eleve n'est pas assez proche de l'interface ;
- l'exercice ne fait pas vraiment choisir un bloc de capteur dans une situation de programme ;
- il faut eviter les faux blocs capteurs non pris en charge par le generateur d'images.

Nouvelle piste a valider :

- type : `qcu` ;
- contexte : un programme micro:bit affiche une information, mais le bloc de capteur a placer est manquant ;
- support : deux choix textuels qui reprennent des noms de blocs visibles dans l'interface, sans les mettre en rendu Blockly ;
- consigne : "Quel bloc faut-il placer dans le programme pour lire l'information demandee ?" ;
- reponses : deux blocs de capteurs possibles, un seul utile pour le besoin ;
- feedback : explique pourquoi le bloc choisi lit la bonne grandeur.

Exemple de structure :

> Le programme doit afficher le niveau sonore autour de la carte.  
> Quel bloc faut-il placer dans l'emplacement vide ?

Reponses :

1. `niveau sonore`
2. `temperature (°C)`

Retour utilisateur : cette forme est retenue si l'interface montre un programme avec un trou, et si l'eleve choisit le bloc a utiliser.

Cadrage CM2 retenu :

- type : `qcu` ;
- contexte : le lien `interface` ouvre le programme micro:bit avec un emplacement vide ;
- consigne : choisir le bloc de capteur a placer dans le trou ;
- reponses : images separees de blocs capteurs proposes par l'interface ;
- solution : le bloc qui fournit l'information demandee ;
- feedback : nomme la grandeur lue par le capteur choisi.
- vocabulaire eleve : eviter d'exiger la connaissance de "capteur de couleurs" ou "LED Neopixel" dans le contexte ; s'appuyer sur les mots visibles dans les blocs et expliquer rouge/vert/bleu comme trois valeurs de lumiere.

### 115-117 - 6e

Type retenu : `qcu`.

Structure :

1. Une consigne de programme est donnee.
2. Quatre programmes courts sont proposes sous forme de captures a produire.
3. L'eleve choisit le programme qui utilise le bon capteur dans le bon contexte.
4. Les reponses sont pour l'instant decrites textuellement ; elles seront remplacees par des captures fournies par l'utilisateur.

But didactique :

- Choisir parmi plusieurs programmes, pas parmi des blocs isoles.
- Verifier que la donnee capteur correspond au besoin.
- Verifier que cette donnee est exploitee au bon endroit du programme : console, afficheur 4 chiffres, jauge, etiquette de demarrage.
- Justifier implicitement l'adequation au besoin par le choix du programme complet.

Exemples de distracteurs :

- bon capteur mais mauvais contexte d'affichage ;
- mauvais capteur dans le bon contexte d'affichage ;
- capteur proche mais qui mesure une autre grandeur ;
- programme avec etiquette de demarrage incoherente.

Cadrage detaille de la serie : voir `115-wip.md`.
